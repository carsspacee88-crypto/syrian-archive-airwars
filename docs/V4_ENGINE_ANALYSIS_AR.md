# تحليل محرك الجمع V4 وإصلاح انهيار السرعة

## الخلاصة التنفيذية

المشكلة في V3 لم تكن بطء الإنترنت ولا ضعف VPS. الدليل من المهمة `0401–0499` هو أن طلبات X احتاجت نحو `0.3ث` على الشبكة، لكنها انتظرت في الطابور حتى `131.8ث` وظهر P90 يساوي `173.6ث`.

كان V3 يرفع فاصل المضيف بعد بعض الاستجابات إلى ثماني ثوانٍ، ثم يجعل الطلبات تنتظر وهي حائزة على حصص العمال. مع 12 عامل منصة أصبح آخر طلب في الموجة ينتظر تقريبًا:

`11 × 8ث = 88ث`

وهذا يطابق الفرق المقاس بين زمن الشبكة والمدة الظاهرة. لذلك لم تكن زيادة العمال من 24 إلى 64 علاجًا؛ كانت تزيد طول الصف وعدد الحصص المحتجزة.

يعالج V4 السبب نفسه: يحجز موعد البدء أولًا، وينام خارج حصص الشبكة، ثم يأخذ الحصة عندما يحين الموعد. لا يبطئ `403` أو `404` كل المضيف، ولا يُمسك `Retry-After` بعامل. كما يفصل الواجهة بين زمن المجدول، pacing، إعادة المحاولة، الشبكة، الاستخراج، والحفظ.

## الأخطاء المكتشفة في V3

1. قفل المضيف كان يُمسك أثناء النوم.
2. الطلب كان يأخذ semaphore المضيف والعالمي قبل انتظار الفاصل.
3. `401/403/408/425/451` كانت تضاعف تأخير المضيف حتى 8 ثوانٍ.
4. التعافي احتاج ثماني نجاحات متتالية؛ فشل متقطع واحد كان يعيد العداد.
5. `429 Retry-After` كان قد ينام داخل الحصة حتى عند عدم وجود محاولة تالية.
6. كل الطلبات كانت تدخل FIFO عالميًا؛ كثافة Facebook/X كانت تؤخر المضيفين النادرين.
7. P50/P90 كانا يخلطان الشبكة بالطابور، ويستخدمان تاريخ محاولات قديمًا.
8. السرعة والـETA كانتا متوسطًا منذ بداية المرحلة، لا نافذة حديثة.
9. JSON-LD كان يُقرأ بعد حذف عناصر `script`، لذلك لم يكن يُستخرج فعليًا.
10. لم يكن هناك استخراج عام لـJSON أو RSS/Atom أو DOCX أو Windows-1256.
11. PDF أو HTML كانا يُحللان داخل event loop، فيتوقف تقدم الشبكة أثناء التحليل.
12. MIME الخاطئ كان قد يحول ملفًا ثنائيًا إلى نص مزيف.
13. الاستجابة البطيئة التي ترسل بايتات متقطعة كانت تتجاوز المهلة لأن مهلة HTTPX مهلة خمول وليست deadline كليًا.
14. cache كان يستطيع أن يثق بـhash دون إعادة حسابه، أو يستبدل نتيجة جيدة بنتيجة أدنى.
15. معاملات `s` و`t` و`ref` كانت معرضة للحذف خارج المواقع التي تكون فيها معاملات تتبع، ما قد يدمج رابطين مختلفين.
16. `media_metadata_preserved` كانت تُعرض كفشل قابل للإعادة رغم أنها اكتمال مقصود حسب سياسة عدم تنزيل الوسائط.
17. كان يُعاد تنفيذ `GROUP BY` على كل المهمة بعد دفعات صغيرة.
18. ملف progress كان ينمو بلا حد ويُعاد `fsync` بصورة مكلفة.
19. زر الاسترداد كان يستطيع إعادة المرور السريع نفسه من دون تفعيل Wayback.
20. Benchmark V3 استخدم ردود `200` فقط، عطّل adaptive pacing، وصغّر التأخيرات، ولم يشمل الحفظ أو قاعدة البيانات؛ لذلك لم يستطع كشف الانهيار الحقيقي.

## تصميم V4

### المجدول

- ترتيب round-robin حسب المحول والمضيف قبل إطلاق المهام.
- GCRA/token reservation لكل مضيف مع burst مضبوط.
- النوم قبل أخذ semaphore، وليس داخله.
- backoff و`Retry-After` خارج الحصص.
- deadline كلي للاستجابة، شامل الجسم والتحويلات.
- إعادة فحص circuit breaker بعد انتظار الحصة حتى لا تنطلق موجة قديمة بعد ثبوت تعطل المضيف.
- `401/403/404` تعد نتيجة رابط؛ لا تنشئ تأخيرًا متضاعفًا للمضيف.
- `429` وحده ينشئ cooldown صريحًا وفق ترويسة الخادم.
- طابور كتابة محدود يمنع تراكم النتائج في الذاكرة.
- فحص pause/cancel كل 250ms وإلغاء المهام غير المحفوظة.

### المحولات السريعة

- Facebook public embed بدل SPA الكامل أولًا.
- X/Twitter oEmbed مع lane مستقل.
- Telegram public embed.
- YouTube oEmbed لحفظ العنوان والناشر كـ`successful_partial` بوضوح، لا كنص كامل أو transcript.
- الصفحة العامة الحية للمواقع الأخرى.
- AMP وJSON alternate عند ضعف الصفحة الأساسية.
- الروابط المؤرشفة المدرجة.
- عدة لقطات Wayback في وضع الاسترداد، وليس لقطة واحدة فقط.

### استخراج النص

- HTML ensemble باستخدام Trafilatura ثم JSON-LD وNext data وDOM الدلالي وfallback محافظ.
- قراءة JSON-LD قبل حذف scripts.
- JSON عام بمفاتيح موثوقة مثل `articleBody`, `body`, `content`, `text`.
- RSS وAtom وXML.
- DOCX من `word/document.xml`.
- RTF والنص الصريح.
- PDF النصي مع sniff من `%PDF-` بدل الاعتماد على MIME فقط.
- اكتشاف UTF-8 وWindows-1256 وWindows-1252 وcharset-normalizer.
- اكتشاف الملفات الثنائية ورفض تسجيلها كنص.
- التحليل في thread pool حتى لا يوقف event loop.
- وسم النص المبتور أو الملخص فقط `successful_partial` بدل ادعاء الاكتمال.

### الجودة والحالات

- `successful`: نص عام كامل مقبول.
- `successful_partial`: نص صحيح لكنه مبتور أو ملخص/metadata جزئي.
- `cached`: نص ناجح سابق تحقق hash الخاص به.
- `embedded_text_preserved`: نص موثوق محفوظ سابقًا.
- `media_metadata_preserved`: اكتمال حسب سياسة عدم تنزيل الوسائط، وليس فشلًا.
- `recovery_deferred`: تعذر خارجي محفوظ للاسترداد، ولا يوقف المهمة.
- `internal_error`: خلل تشغيلي حقيقي فقط.

لا تُحوّل V4 صفحة تسجيل دخول أو CAPTCHA أو Cloudflare shell إلى نجاح. تحفظ سبب التعذر وHTTP status وآخر محول جُرّب. كما لا تسمح لنتيجة مؤجلة أو جزئية باستبدال cache ناجح كامل.

### الاستمرارية والتخزين

- SQLite/WAL دائم لـURL cache بدل إعادة كتابة JSON كامل.
- writer واحد متسلسل للملفات، يعمل خارج event loop.
- تحديثات لوحة الإدارة مجمعة في دفعات.
- عدادات PostgreSQL تُحدّث تفاضليًا بدل GROUP BY متكرر.
- progress يحتفظ بفهرس استئناف مضغوط؛ التفاصيل الكاملة تبقى في ملف المصدر وDB.
- آخر 5000 timing فقط تبقى في نافذة القياس، مع aggregate عام.
- checkpoint الافتراضي الكبير لا يهدد الاستئناف: كل مصدر يُحفظ منفردًا، وعند restart تُعاد ماديته من checkpoint دون طلب شبكة جديد.
- زر «استرداد المتعذر» يفعّل Wayback ويعيد العناصر المؤجلة/التشغيلية فقط.
- منع downgrade من إصدار أحدث إلى V4.

## ما يمكن وما لا يمكن ضمانه

يمكن ضمان أن فشل مصدر خارجي واحد لا يوقف المهمة، وأن كل نتيجة تصنف وتُحفظ، وأن النجاح لا يُختلق. لا يمكن لأي برنامج عام أن يضمن نصًا من صفحة خاصة، محذوفة، خلف تسجيل دخول، CAPTCHA، اشتراك، حظر جغرافي، أو خادم متوقف. V4 لا تتجاوز الحماية ولا تستخدم stealth؛ تنقل هذه الحالات إلى الاسترداد مع دليل واضح.

## اختبارات القبول

تتضمن حزمة V4 اختبارات مستقلة للحالات الآتية:

- `403 → 200` متناوب لا يخلق تأخيرًا متضاعفًا.
- `429` مع محاولة واحدة لا ينام.
- backoff لا يحجز العامل العالمي.
- slow-drip يتوقف عند deadline الحقيقي.
- circuit يوقف الموجة التي انتظرت بعد ثبوت العطل.
- مضيف نادر يظهر في أول عناصر الجدولة رغم 140 رابطًا اجتماعيًا.
- JSON-LD وJSON وRSS وAtom وDOCX وWindows-1256.
- عدم دمج روابط عامة تختلف في `s/t/ref`.
- المقاييس لا تجمع محاولات تشغيل قديم مع التشغيل الحالي.
- النص المبتور لا يصبح اكتمالًا كاملًا.

## تفسير رقم السرعة

عدد «العمال» ليس سرعة. السرعة الصحيحة هي عدد العناصر المحسومة خلال نافذة حديثة، بينما المقاييس التالية تُعرض منفصلة:

- throughput لآخر 30/60/300 ثانية.
- backlog لكل lane.
- scheduler wait.
- host pacing wait.
- retry wait.
- network time.
- persist time.

إذا كان الإنترنت 0.3ث والطابور 100ث، فالمشكلة جدولة. إذا كانت الشبكة نفسها 6ث، فالمشكلة خارجية ويجب الانتقال إلى recovery بدل حبس آلاف العناصر خلفها.
